    Claves primarias y foráneas

    Las claves primarias y foráneas son fundamentales en bases de datos relacionales.

    Si son bases de datos relacionales, es porque nos permiten relacionar datos en diferentes tablas.

    El problema de no usar múltiples tablas

    Se nos da el siguiente problema a resolver:

    Una tienda especializada en gatos necesita llevar un histórico de sus clientes. Se nos pide un sistema que permita registrar los clientes, junto a sus gatos. Cada gato deberá tener una breve descripción de los colores de su pelaje.

    Podriamos crear una tabla como esta:

    nombre email nombre_gato colores sexo
    Diego diego@gmail.com mambo gris, blanco M
    Manolo manolo@gmail.com mandarina naranja M
    Maria maria@gmail.com meowcifer negro M
    Javier javier@gmail.com micifu blanco, negro, naranja H
    Elvira elvira@gmail.com sardina naranja, blanco H

    Los datos que nos solicitan están ahi, pero tenemos múltiples problemas con esta estructura.

    Repetición

    En la columna de colores estamos repitiendo continuamente las mismas palabras. Cuanto más crezca la tabla, más pesará y más redundancia de datos encontraremos. Además, no vamos a tener tanta variedad de colores como para dejar un campo.

    Valores atómicos

    Cada columna debe representa un dato, la columna de colores tiene múltiples.

    Buscar valores dentro de esa columna será mucho mas complicado y costoso, si queremos buscar todos los gatos que tienen el color blanco:

    SELECT * FROM gatos WHERE colores LIKE '%blanco%'

    Esta operación es más lenta y costosa de calcular, debe coger cada fila, buscar a lo largo de todo el string de los colores y buscar una coincidencia.

    Además, evitaremos errores e inconsistencias, si tuvieramos una tabla de colores como esta:

    id nombre
    1 blanco
    2 negro
    3 gris
    4 naranja

    Siempre podremos referenciar blanco, en lugar de Blanco, BLANCO o Blnaco.

    Entidades separadas

    Cada tabla representa una entidad a la que representar. Aqui estamos mezclando tres entidades completamente diferentes:

    • Clientes
    • Gatos
    • Colores

    Cuando las dejamos en una sola, la responsabilidad de cada columna se pierde.

    ¿El email es del gato? ¿El sexo es del cliente o del gato? ¿El cliente es blanco o naranja?

    Además nos obliga a comenzar a usar nombres para columnas específicos, nombre y nombre_gato es muy inconsistente y nos obliga a recordar que es nombre_gato y no gato_nombre.

    Solución

    Si separamos cada entidad en una tabla separada:

    id nombre
    1 blanco
    2 negro
    3 gris
    4 naranja
    id nombre email created_at
    1 Elvira elvira@gmail.com 2026-09-04 07:12:14
    2 Javier javier@gmail.com 2026-09-04 07:12:14
    3 Manolo manolo@gmail.com 2026-09-04 07:12:14
    4 Maria maria@gmail.com 2026-09-04 07:12:14
    5 Diego diego@gmail.com 2026-09-04 07:12:14
    id nombre sexo cliente_id created_at
    1 sardina H 1 2026-09-04 07:12:14
    2 micifu H 2 2026-09-04 07:12:14
    3 mandarina M 3 2026-09-04 07:12:14
    4 meowcifer M 4 2026-09-04 07:12:14
    5 mambo M 5 2026-09-04 07:12:14
    gatito_id color_id
    1 4
    1 1
    2 1
    2 2
    2 4
    3 4
    4 2
    5 3
    5 1

    Clave primaria (PK)

    La clave primaria sirve para identificar de manera única cada fila en una tabla. Y nos permite referenciarla en otra tabla.

    Es diferente a UNIQUE, aunque ambos evitan duplicados, la clave primaria:

    • No puede repetirse.
    • No acepta valores nulos.
    • Solo puede existir una clave primaria por tabla.
    • Identifica de manera única cada fila.
    • Se puede usar fuera de esa tabla.

    Imagina el siguiente caso:

    CREATE TABLE clientes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  nombre TEXT NOT NULL,
  email TEXT NOT NULL UNIQUE
);

    Aqui, tanto id como email identifican de manera única cada fila. Pero el valor id es la clave primaria.

    Por un lado, queremos asegurarnos de no tener email con duplicados en una base de datos, pero no es buena idea usarlo como identificador de la fila, un id es más pequeño de almacenar y recorrer, el email puede cambiar, y las relaciones serán mas simples.

    La clave primaria además asegura más velocidad a la hora de realizar busquedas, ya que se crea un indice separado de manera interna.

    Clave foránea

    Las claves foráneas se utilizan para referenciar claves primarias de otras tablas, es la forma en la que creamos relaciones entre tablas:

    CREATE TABLE clientes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  nombre TEXT NOT NULL,
  email TEXT NOT NULL UNIQUE
);

CREATE TABLE gatos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  nombre TEXT NOT NULL,
  sexo TEXT NOT NULL,
  cliente_id INTEGER NOT NULL,
  CHECK (sexo IN ('H', 'M')),
  FOREIGN KEY (cliente_id) REFERENCES clientes(id) ON DELETE CASCADE
);

    Ahora cada gato tiene un id único que le identifica, puede haber gatos con el mismo nombre, y cada gato tiene un dueño que referencia al id de la tabla clientes.

    Tipos de relaciones

    Según configures tus claves primarias y foráneas, podrás crear diferentes tipos de relaciones:

    Uno a uno (1:1)

    Una fila solo se puede relacionar con otra fila.

    En el ejemplo anterior, un gato solo puede tener un dueño, el que ocupa la columna cliente_id.

    Uno a muchos (1:N)

    Una fila puede relacionarse con múltiples filas de otra tabla. Pero no al revés.

    En nuestro ejemplo, un cliente puede tener múltiples gatos, pero un gato solo tiene un dueño.

    La dirección importa cuando piensas en relaciones, no es lo mismo:

    cliente -> gato (1:N)
gato -> cliente (1:1)

    Muchos a muchos (N:M)

    Por último, esta relación indica que varias filas de una tabla pueden relacionarse con múltiples filas de otra tabla.

    ¿Cuantos colores puede tener un gato? Muchos.

    ¿Cuantos gatos pueden usar un color? Muchos.

    En estos casos, utilizaremos una tabla intermedia:

    CREATE TABLE gatitos_colores (
  gatito_id INTEGER NOT NULL,
  color_id INTEGER NOT NULL,
  PRIMARY KEY (gatito_id, color_id),
  FOREIGN KEY (gatito_id) REFERENCES gatitos(id),
  FOREIGN KEY (color_id) REFERENCES colores(id)
);

    Ahora tenemos una tabla exclusivamente dedicada a almacenar las relaciones entre las tablas colores y gatos, usando los id de cada una de esas tablas.

    La clave primaria es compuesta, utiliza dos valores para identificar cada fila, si hicieramos esto:

    CREATE TABLE gatitos_colores (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  gatito_id INTEGER NOT NULL,
  color_id INTEGER NOT NULL,
  FOREIGN KEY (gatito_id) REFERENCES gatitos(id),
  FOREIGN KEY (color_id) REFERENCES colores(id)
);

    Podríamos acabar con un gato que tiene multiples veces el mismo color.

    Activando las FK

    Da igual que definas claves foráneas en SQLite, debes activar que la base de datos realmente haga uso de las mismas con:

    PRAGMA foreign_keys = ON;

    Al principio de tu schema.

    Los PRAGMA son comandos especiales únicos de SQLite, sirven para modificar ciertos comportamientos de la base de datos y extraer información especial de las tablas.
